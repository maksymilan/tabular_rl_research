# TRUST-SQL 风格 GRPO checkpoint-1 奖励—策略诊断

生成日期：2026-08-11

## 范围与协议

本报告只分析正式训练第一个 optimizer update 对应的 240 条在线轨迹（30 个问题，每题 K=8），不启动新训练、不占用 GPU，也不把后续不同题目的 rollout 当作训练前后行为对照。

| 项目 | 配置 |
|---|---|
| 初始策略 | Qwen2.5-Coder-7B-Instruct + SFT2 checkpoint-1682 |
| SFT2 adapter SHA256 | `d880e2d7cc3203fdb0d11a7c188d8f607fd297b174eff23f741b6fe73cc3ce6e` |
| 工具协议 | atomic `version36`, hash `20a8d3b4356d883c` |
| 算法 | result-only GRPO，无 rank loss、无 KL loss |
| 奖励 | 正确 `1.0`；可执行但错误 `0.2`；不可执行 `0.0` |
| 相对组 | 每题 K=8，组内标准化 advantage |
| 策略损失 | `trajectory_token_mean`；整条模型响应均可训练 |
| 学习率 | `8e-7` |
| 数值精度 | LoRA 参数与 Adam 状态均为 FP32 |

## 一、参数是否真的发生了更新

| 证据 | checkpoint-1 结果 | 判断 |
|---|---:|---|
| 梯度范数 | 0.074101 | 存在非零反向信号 |
| LoRA 原始参数更新 L2 | 0.061742 | 非零 |
| 原始更新 / SFT2 参考参数 | 0.167800% | 小但可测 |
| 有效 LoRA 权重更新 L2 | 0.035556 | 非零 |
| 有效更新 / SFT2 有效权重 | 0.160500% | 小但可测 |
| FP32 LoRA tensor | 392/392 | 通过 |
| FP32 optimizer tensor | 1176/1176 | 通过 |

结论：checkpoint-1 不是“训练代码完全没有改变模型”。它已经产生真实、数值可测的参数更新；但更新幅度只有约 0.16%，是否足以改变任务能力，必须依赖同题行为对照或完整 dev 评测，不能仅从参数距离推出。

训练日志里的标量 `loss=0.0` 不表示梯度为零。第一个 update 计算时新旧策略相同，ratio 约为 1；组内标准化 advantage 的均值又接近 0，因此记录的 surrogate loss 可以正好抵消为 0，但各样本对 log-prob 的导数仍非零，和 `grad_norm=0.074101`、实际 LoRA 位移相符。

## 二、奖励和惩罚如何落到轨迹上

| Advantage 符号 | 轨迹数 | 占比 | 正确 | 合法 | 平均 turns | 参与反向 |
|---|---:|---:|---:|---:|---:|---|
| 正 | 114 | 47.5% | 108 | 114 | 8.16 | 是 |
| 负 | 86 | 35.8% | 0 | 41 | 8.98 | 是 |
| 严格零 | 40 | 16.7% | 32 | 40 | 6.35 | 否 |

- 30 个 K8 组中，25 个是异质奖励组，5 个是同质组。
- 200/240 条轨迹得到非零 advantage；40 条来自同质组的轨迹严格为零。
- 1956 个策略 turn/transition 中，1702 个参与反向，254 个没有梯度，空信号比例为 12.99%。
- `tiny_nonzero=0`：同质组没有因数值误差得到伪小梯度。
- 每组 advantage 和的最大绝对值为 `1.67e-6`，在 `2e-6` 容差内。
- 整条模型响应的可训练 token 比例为 100%，因此不是只训练 action token；推理内容和工具调用内容共同受到同一个轨迹 advantage。

### 奖励档位与相对优势

| 奖励 | 轨迹 | 正优势 | 负优势 | 零优势 | 平均 advantage |
|---:|---:|---:|---:|---:|---:|
| 0.0 | 45 | 0 | 45 | 0 | -1.078854 |
| 0.2 | 55 | 6 | 41 | 8 | -0.468480 |
| 1.0 | 140 | 108 | 0 | 32 | +0.530820 |

信用方向没有发生档位反转：`0.0` 从未得到正优势，`1.0` 从未得到负优势。`0.2` 的符号取决于同组其余 7 条轨迹：当同组更差的 `0.0` 较多时，它可以得到正优势；当同组有更多 `1.0` 时，它通常为负。这正是 GRPO 的相对优化含义，而不是代码随机分配。

## 三、工具暴露在正负轨迹中的分布

下表按工具调用出现次数统计。它表示某工具出现在正/负 advantage 轨迹中的频率，不等于该工具调用本身被独立判定为正确或错误。

| 工具 | 正优势轨迹内次数 | 负优势轨迹内次数 | 零优势轨迹内次数 | 非零信号中正向占比 |
|---|---:|---:|---:|---:|
| `answer_from_context` | 114 | 41 | 40 | 73.5% |
| `condition_filter` | 253 | 185 | 68 | 57.8% |
| `describe_table` | 135 | 110 | 43 | 55.1% |
| `extreme_value_select` | 15 | 4 | 2 | 78.9% |
| `group_aggregate` | 76 | 61 | 15 | 55.5% |
| `inspect_column` | 37 | 46 | 10 | 44.6% |
| `join_tables` | 82 | 60 | 6 | 57.7% |
| `project` | 59 | 27 | 25 | 68.6% |
| `read_subtable` | 96 | 87 | 42 | 52.5% |
| `scalar_compute` | 40 | 17 | 0 | 70.2% |

不能据此断言 `inspect_column` 应被惩罚，或 `extreme_value_select` 应被奖励。一个工具可同时出现在最终成功和最终失败的轨迹中；当前 result-only GRPO 没有工具级 verifier 去拆分这种混合。

## 四、失败和恢复信号

首批 240 条的结果分布为：正确 140、可执行但答案错误 55、不可执行 45。45 条不可执行轨迹包括：protocol error 18、no-progress error 13、argument validation error 9、context overflow 4、timeout 1。

值得注意的是，正优势轨迹中有 50 个带 `feedback_recovery` 标记的 turn，奖励 1.0 的正确轨迹中共有 51 个这类 turn。这说明环境报错后的成功恢复并没有被一概判负；只要整条轨迹最终优于同组样本，报错前后的整段生成都会得到正 advantage。相反，负优势轨迹中有 148 个 recovery turn，它们会随最终失败一起受罚。

## 五、能否说明奖励到了“正确关键路径”

当前证据能确认的是：

1. 奖励档位、K8 分组和 advantage 方向实现正确；
2. 非零 advantage 确实形成梯度并改变了 LoRA 参数；
3. 推理 token 与工具调用 token 都参与训练，不存在只改浅层 action 语法的问题。

当前证据不能确认的是：

1. 成功轨迹中的每个中间推理和工具调用都正确；
2. 失败轨迹中的每个中间动作都应被惩罚；
3. 梯度集中在导致成败的第一处分岔或关键关系操作上。

原因是 result-only GRPO 给一条轨迹中的所有模型 token 使用同一个 episode-level advantage。它优化的是“同题 K8 中整条轨迹的相对偏好”，不是 step-level 或 token-level 的因果信用。于是，最终成功但中途绕路/报错的轨迹会整体被强化；最终失败但包含若干合理中间动作的轨迹会整体被压低。

因此，对 checkpoint-1 最准确的描述是：**训练管线和相对奖励方向已经真实工作，但关键路径信用是否精确仍未被这个 baseline 验证。**

## 六、策略能力是否已经改变

训练文件目前没有可用的同题训练前后配对：`policy_global_step=0` 的 30 题与后续 `policy_global_step=1` 已生成的题目不重合，same-task pair 数为 0。后续样本的更高在线正确率不能直接归因于 checkpoint-1，因为题目不同。

所以当前可以确认“参数变化真实”，尚不能只凭训练 rollout 确认“能力变化真实”。该问题应由正在进行的 checkpoint-1 固定 BIRD-dev greedy 评测回答；在评测完成前，不使用不同题目上的在线 reward 差值宣称收益。
