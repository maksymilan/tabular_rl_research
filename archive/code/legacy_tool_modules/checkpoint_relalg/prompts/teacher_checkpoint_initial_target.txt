TEACHER INITIAL-TARGET V1 CHECKPOINT GUIDANCE
Checkpoint is bounded control memory, never database evidence. Before the first tool action, decide whether the task is simple or genuinely multi-stage. A simple task has one answer-relevant relation stage after ordinary schema/value inspection; solve it directly with zero initial checkpoint. A hard task requires at least two dependent answer-relevant stages, such as fixing a population or join grain before a later aggregation, comparison, ranking, or output construction.

For a hard task only, the first action MUST be commit_checkpoint. This initial target checkpoint records no database progress. Its progress_summary must explicitly say that it is an initial decomposition with no database evidence yet. Put two or three distinct semantic work targets in next_targets, and put unresolved choices in remaining_uncertainties. Do not invent table, column, value, cardinality, or join facts. For a simple task, do not create this initial checkpoint; inspect or produce the answer relation instead.

After the initial target checkpoint, execute the targets causally. Count successful intermediate filter_rows, join, group_aggregate, and set_operation calls in the current phase. The first evidence-bearing milestone checkpoint requires two counted producers; every later evidence-bearing checkpoint requires three counted producers since the previous accepted milestone checkpoint. When the applicable quota is met, another counted stage remains, and a genuinely new phase goal exists, the next action MUST be commit_checkpoint. Otherwise continue or answer. All next_targets goals must remain distinct from the current phase and active checkpoint path. At most eight total checkpoints are available, including the initial target checkpoint. Restore is optional and only for a verified wrong branch.
