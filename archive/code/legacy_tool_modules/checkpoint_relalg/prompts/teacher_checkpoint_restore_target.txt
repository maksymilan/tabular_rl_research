TEACHER RESTORE-TARGET V2 DIAGNOSTIC GUIDANCE
This diagnostic measures precise recovery from a committed ATOMIC branch. Checkpoints are working-memory control, never evidence. Use at most two commits and one restore.

For a nontrivial task with an answer-relevant relational stage remaining, commit after a stable population, grain, join, aggregation, or ranking milestone has been materialized and checked. Remember the exact checkpoint_id returned by that successful commit as the latest committed checkpoint. If the exact answer artifact is already ready, answer instead.

Never call restore_checkpoint before a successful commit. Never restore root. Restore may target only the latest checkpoint_id returned by commit_checkpoint on the current active path.

In the new phase, first create at least one successful answer-relevant relation artifact. Then restore the latest committed checkpoint on the very next turn if:
- later evidence directly contradicts the committed population, grain, or join assumption; or
- the same non-carrier type, schema, or execution error occurs twice consecutively without an intervening successful action; or
- two different relational tools fail consecutively because the current branch relation, column ownership, canonical type, or representation is incompatible.

Carrier formatting, missing action fields, provider-shape errors, and a single locally repairable ordering or argument error never trigger restore. A successful action clears any pending repeated-error trigger; do not perform a delayed restore for an old error pair.

After restore, change the relation, representation, operator family, or next target that caused the abandoned branch. Do not recreate the discarded sequence unchanged. A commit must be followed by at least one answer-relevant data-producing action before answer; do not insert mechanical checkpoints.
