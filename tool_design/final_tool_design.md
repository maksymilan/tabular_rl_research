# Final Tool Design (canonical, finalized 2026-06-06)

This is the **finalized** tool design. It supersedes the earlier iteration captured in
`tool_usage.md` / `tool_io_spec.json` / the old `trajectory/` examples (those predate the
finalization and will be regenerated by the SQL→tool compiler). Rationale and the long
design discussion live in `../draft/`.

Goal: the tool set must be able to express **any Spider/BIRD gold SQL** (so gold SQL can be
compiled into faithful tool trajectories), plus one beyond-SQL capability (`semantic_match`).
Positioning is unchanged: we are not more expressive than SQL — we are an **atomic,
instrumented decomposition** of SQL over materialized state, which is what enables
process-level credit assignment and evidence-grounded answers.

## 1. State model (3 stores + catalog, no drop, no persistent subtable)

- `data_view` (harness-side): the real table store. Holds **source tables + derived tables**
  (`kind`: `source` | `filter` | `group` | `join` | `derive` | `setop` | `window`), each stored
  as a **re-materializable definition**, possibly large, never fully in the prompt. The model
  sees only **handles** (table_name, columns+types, row_count, optional intent).
- `static_task_memory` (model-visible): model-authored conclusions + harness-authored metadata.
  Every item **references** `data_view` ground truth (rows/cells) or tool-history steps; at
  render time the harness **expands** referenced cells inline. Memory never stores verbatim
  source data as its own authority.
- `dataset_overview` (model-visible, init): catalog of source-table handles + `relations`
  (PK/FK with cardinality) + full-table numeric stats.
- `tool_history` (internal): normalized calls, outputs, provenance; for dedup/analysis/reward.

There is **no persistent `dynamic_table_context` object** and **no `drop_context` tool**.
Perception happens through **transient tool results** in the ReAct transcript. Compression =
acquisition restraint (small `top_k`, aggregate-not-read, summarize-to-memory); the harness may
auto-compact old row-bearing results.

**Uniform citation rule (critical):** every row the model ever sees is addressable by
`(table_name, row_id)`, regardless of which tool produced it. Table-creating tools name their
output so its rows are addressable; row-returning tools return rows of an existing table with
that table's row_ids. Derived rows (group/join/window) carry synthetic ids whose provenance
expands to source rows in tool_history.

## 2. Tool set

Interaction envelope: ReAct `<think>` / `<tool_call>{json}</tool_call>` / `<tool_response>` /
... / terminal `answer_from_context`. The model emits only `<think>` + `<tool_call>`.

|---|---|---|---|---|
| 1 | `inspect_column` | (table, column) | distinct/frequent values + format (NO numeric aggregates) | high |
| 2 | `read_subtable` | (table, rows[ids\|head:k\|sample:k], columns) | a rows×columns block (transient) | high |
| 3 | `condition_filter` | (table, conditions[{column\|expr, op, value\|column\|expr}], [preview_k, return_columns]) | **creates `filter` table**; optional inline preview. Subsumes old entity_match via `=`/`contains` | high |

~12 core + `window`/`semantic_match` as lower-frequency/optional. `semantic_match` is the only
non-SQL tool.

## 3. Expression sublanguage (the cross-cutting enabler)

`derive_column`, `condition_filter`, and `aggregate`/`group_aggregate` all accept **scalar
expressions**, not just `column op literal`. The sublanguage mirrors SQL scalar expressions:
arithmetic (`+ - * / %`), comparison/boolean (`AND OR NOT`, parens), `CASE WHEN`, `CAST`,
string functions (`SUBSTR`, `LIKE`, `LOWER`, `CONCAT`, ...), date functions (`YEAR`, `DATE_DIFF`,
...), and column references (`table.col`). This single sublanguage closes computed columns,
`SUM(expr)`, column-vs-column predicates (`a.x > b.y`), `CASE`, `IN`, `IS NULL`, `LIKE`.

## 4. SQL coverage

Directly mapped: SELECT(project), WHERE(filter), INNER/LEFT/RIGHT/FULL/CROSS JOIN, GROUP BY +
aggregates, ORDER BY...LIMIT k (extreme), DISTINCT (group-by no agg), UNION/INTERSECT/EXCEPT
(set_op), window functions (window), computed columns/expressions (derive_column + expr).
Via composition: HAVING (group → filter), scalar subquery (aggregate → filter literal),
correlated subquery (group → join → filter on column), subquery-in-FROM (derived tables).
Beyond SQL: `semantic_match`. With the expression sublanguage + set_op + window + extended
join/agg ops, the set covers essentially all Spider/BIRD SQL.

## 5. Reward (summary; full formalization in ../draft/process_reward_density.md)

- **Correctness gate**: only reward when the final answer is correct (terminal verification:
  exact/execution match for structured; external stronger-model judge for free-form).
- **Relevance/sufficiency**: for structured answers, deterministic — the answer must be
  re-derivable from exactly the cited evidence, and the cited evidence must lie in the answer's
  computational **provenance slice**; for free-form, the external judge scores evidence support.
- **Process credit (v1, lenient)**: reward steps in the correct answer's provenance slice;
  penalize off-slice (provably wasteful) steps. Pivotality/counterfactual deferred (escalate
  if bloat appears). No `drop`; compression measured as total cells read.

## 6. Action space & learnability (summary)

Nominal ~12 tools; effective space ≈ tools × modes × expression-sublanguage ≈ decomposed SQL.
But each action is one small, structured, harness-validated tool call (easier than emitting a
whole query). Learnable: an 8B model (TableGPT-R1) learned a **larger, less-structured**
code-execution space; ours is more constrained, with SFT warm-up from compiled gold-SQL
trajectories + dense process reward + execution validation. Scope dial: compile only the
simple/medium Spider subset for v1 (skip window/nested set-ops) to shrink the effective space.

## 7. Data construction

- **Compile mode** (Spider/BIRD, have gold SQL): parse gold SQL → emit tool sequence → execute
  via harness → verify result == execute(gold SQL) → `label_assessment=accepted`. Question is
  the dataset's; answer is executed (never generated).
- **Sample-and-filter mode** (only gold answer, e.g. WTQ/TableBench): strong model proposes a
  tool trajectory → execute → keep iff answer == gold (rejection sampling + multi-model consensus).
- **Fuzzy-matching data** (so `semantic_match` is exercised — SQL never uses it): see §8.

## 8. Constructing semantic_match (fuzzy) data

SQL compilation never produces `semantic_match` (SQL has no fuzzy matching). Three sources:

1. **Literal-fuzzing augmentation (scalable, from the Spider pipeline)**: take a compiled
   trajectory whose `condition_filter(col = 'exact value')` matches a question literal; **perturb
   that literal in the question** to a synonym/alias/description (`"New York" → "the Big Apple"`,
   exact category → semantic description) using a known alias table or an LLM, **verifying the
   perturbed surface still resolves to the same exact value**. Replace the `condition_filter(=)`
   step with `semantic_match(col, perturbed_query)`. The gold answer (from the original exact SQL)
   is unchanged. This yields (fuzzy question, gold answer, semantic_match trajectory) directly
   from clean SQL data.
2. **Naturally-fuzzy datasets**: WikiTableQuestions / FeTaQA questions that reference entities by
   paraphrase/description → sample-and-filter trajectories using `semantic_match`.
3. **LLM-generated semantic questions** over real tables (ask about an entity by description, not
   name) → resolve gold by exact match → build the semantic_match trajectory → rejection-sample
   for correctness.

Invariant in all three: the **answer comes from execution / exact resolution**; only the
**question surface** is fuzzy, and the correct trajectory must use `semantic_match` because
exact match fails.

## 9. Open / scope

- Selection lifecycle: never deleted within a task; identical predicates deduped; different
  selections never auto-merged (use `set_op`). Re-materialization must pin row order + ids.
- `window` and nested set-ops are scopeable for v1.
- Text/passages (table+text datasets): `document_context` twin + `passages` citations, per
  `../draft/table_text_handling.md` (pending; spec-first before first FinQA trajectory).
