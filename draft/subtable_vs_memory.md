# 子表 vs memory：两个存储的职责划分（draft）

> 草稿 / 讨论记录，非定稿。日期 2026-06-06。
> 主题：在两存储架构（dynamic_table_context 子表 + static_task_memory）下，回答两个疑问——
> (1) 多表场景下子表是否该是多表形式；(2) 引入 memory 后子表是否还有存在必要，会不会被 memory 取代。
> 约定：纯文本，不用 LaTeX。

---

## 0. 起因

最初动机：通过构造"子表"让模型只看到表中最关键的信息，实现上下文压缩。
后来发现表格中间过程会产生有用信息（派生标量、跨表判断等），于是引入 memory。
引入 memory 后产生疑虑：子表的作用还剩什么？是不是只靠 memory 就够模型作答了？（这是审稿人会戳的点。）

---

## 1. 多表子表：是，而且现有设计已经如此

- `dynamic_table_context.tables` 本来就是一个**列表**，每个元素是一张表的矩形切片（各自的 table_name / columns / rows / data）。
- 默认就是**多个互不对齐的子表**：从 users 取若干行列、从 orders 取若干行列，各自矩形、不强行对齐。这正是"跨表行列不对齐"的正确处理——不对齐就放成多个切片。
- 真正需要"按行对齐成一张表"时，那是 join_tables 的职责：它在 data_view 里物化一张已对齐的派生连接表，模型再读它的一个切片。

原则：
```
"几张各自独立的表切片" 是常态；
"一张对齐的表" 只在显式 join_tables 后出现。
```
结论：不用改，确认此原则即可。

---

## 2. 子表必要性：依赖关系被搞反了

错误心智模型：
```
"memory 存结论、子表存原始数据；结论既然进了 memory，原始数据就冗余。"
```

正确心智模型：
```
子表    = 模型感知和操作的"逐字 ground truth"（perception 层）
memory  = 模型对它的"已解释、且必须指回子表"的认知残留（cognition 层）
=> memory 寄生在子表之上，memory 索引子表，永不取代子表作为证据。
```

两层对照：

| 维度 | 子表 dynamic_table_context | memory static_task_memory |
|---|---|---|
| 是什么 | 逐字单元格，原表怎么存就怎么是 | 模型写的结论/事实/计划/排除项 + harness 元数据 |
| 谁产生 | harness 物化（可信，ground truth） | 模型写（可能幻觉） |
| 作用 | 感知层：被工具 filter/max/group 操作；压缩的旋钮 | 认知层：已得出的标量结论、跨表判断 |
| 验证 | 它本身就是证据 | 必须指回子表单元格/步骤才可信 |
| 生命周期/预算 | 受 context_budget 控制，可被 drop | 轻量、持久 |

核心结论：**memory 的价值依赖子表在场来做 grounding，所以 memory 永远不可能让子表冗余。**

---

## 3. 为什么"只有 memory"会失败（4 条）

1. **memory 变成不可证伪的模型主张** → 退化成 CoT/记忆 agent，没有证据 grounding。
   而"证据可引用、可审计、过程奖励可算"正是相对 TableGPT-R1 的全部 novelty。
   砍掉子表 = 砍掉论点。
2. **没法在标量上操作**：不能对一个 memory item 跑 extreme_value_select。要继续算，必须有原始行在场。
3. **逼模型过早总结**：只有 memory 的话，模型得在还不知道问题要什么时，就把看到的一切总结进 memory——而总结正是丢信息/产幻觉的地方。子表让模型先握住原始证据、晚点再下结论。
4. **压缩这个研究对象消失**：最初目标"控制模型看到哪些关键数据"发生在子表层（retrieve/drop）。memory 不压缩表，它存派生事实。没有子表，就没有"可见行的 context budget"可优化。

一句话：审稿人问"是不是 memory 就够了"，本质是在问"是不是让模型用自己未经验证的主张作答就够了"——不够。

---

## 4. 审稿人担心里那点"真的成立"的内核

对**聚合类问题**，作答那一步子表的行可能已被 drop，答案来自一条 memory 的 derived_fact（如 max=12），看起来"作答时子表是空的"。

这是设计预期，不是子表无用：
- 子表在过程中是必需的（要读、要 filter、要算）；
- 那条 memory 事实的 provenance 仍锚在（已 drop 的）子表行 + tool history 上——正是过程奖励/引证忠实度要用的轨迹；
- "作答时子表为空" != "子表无用"，只是说"这题答案是个派生标量，证据轨迹在历史里"。

对**查找/抽取/列表类问题**，答案就是原始单元格/原始行——模型必须直接从子表作答，绝不该先把单元格背进 memory（那才是幻觉入口）。

类比：屏幕上的电子表格（子表）vs 你记的笔记（memory）。不会因为记了"平均=50"就把表格关掉。

---

## 5. 把"设计争论"变成"实测结论"（最稳的回应）

消融实验：
```
A: memory-only      —— 不给子表，模型只能写/读 memory 作答
B: 子表 + memory    —— 现状
```
按问题类型分别测 幻觉率 / 引证忠实度 / 准确率。

预测：A 在查找/抽取类和忠实度上会崩，B 明显更稳。
这样"子表必要性"就成为被验证的命题，而非设计断言。
注：这与 process_reward_density.md 里的 rho_fid / faithfulness 实验是同一套设施。

---

## 6. 可写进设计文档（tool_usage.md 状态模型节）的原则

```
子表在感知/预算控制下持有逐字 ground-truth 单元格；
memory 持有模型写的已解释事实，且每条必须引用子表单元格或 tool-history 步骤。
memory 索引子表，永不取代子表作为证据。
还在看/还要操作的原始数据 -> 子表；已得出的结论（带证据指针）-> memory。
```

这条原则一旦写清楚，"两个存储是否冗余"就不再 ad hoc：它们是"感知 vs 有据认知"两层，职责、信任级、生命周期都不同。也闭合了最初"memory 会不会让子表多余"的纠结——不会，因为方向是 memory 依赖子表。
